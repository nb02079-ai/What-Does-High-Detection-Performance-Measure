## 1. 한 줄 요약

CIC-MalMem-2022로 9개 모델을 비교해 XGBoost로 이진 분류 99.98%를 얻은 **수업 과제 보고서**다. 그런데 한계 절에서 **같은 샘플의 덤프가 학습과 시험에 섞이는 누수 문제**와 **정상 샘플에 식별자가 없어 묶을 수 없다는 문제**를 정확히 짚었다.

## 2. 왜 이 논문을 읽나

이 논문은 본 연구에서 **두 번 다르게 평가된** 문헌이다.

| 시점 | 평가 | 결정 |
|---|---|---|
| 초록만 읽었을 때 | "99.98%"를 보고한 수업 과제 보고서 — 선행 연구로 묶기엔 출처의 무게가 다름 | 원고에서 **제외**하기로 (반영 대기 #17) |
| 본문을 다 읽었을 때 | 본 연구 표 1의 핵심 쟁점(같은 실행 누수, 정상 식별자 부재)을 **먼저 지적한** 문헌 | ✅ 범위 근거에서는 제외하고, **누수를 먼저 지적한 문헌으로 4.1 표 1 각주에 인용** (수업 과제 보고서임을 명시) |

**출처의 성격**(동료 심사 여부)과 **내용의 가치**는 따로 판단해야 한다는 것을 보여주는 사례다. 그리고 초록만 읽고 판단하면 놓치는 것이 있다는 것도.

## 3. 미리 알아둘 개념

| 개념 | 쉬운 설명 |
|---|---|
| **데이터 누수** | 시험에 쓸 정보가 학습 과정에 흘러 들어가 성능이 실제보다 좋게 나오는 것 |
| **그룹 단위 분할** | 서로 관련된 샘플(같은 실행의 덤프들)을 한 묶음으로 보고, 묶음 단위로 학습·시험에 나누는 방식 |
| **최소-최대 정규화** | 각 특징을 [0, 1] 범위로 맞추는 전처리. 학습 데이터에서만 최소·최대를 구해야 누수가 없다 |
| **PCA** | 고차원 데이터를 정보를 가장 많이 담은 몇 개의 축으로 줄이는 기법. 2차원으로 줄여 그림으로 보면 클래스가 얼마나 떨어져 있는지 볼 수 있다 |
| **균형 정확도** | 클래스별 재현율의 평균. 클래스 수가 다를 때 정확도보다 공정하다 |

## 4. 무엇을 했나

| 항목 | 내용 |
|---|---|
| 과제 | ① 이진 분류(정상/악성) ② 4클래스 분류(정상, 랜섬웨어, 스파이웨어, 트로이 목마) |
| 데이터 | Kaggle에 올라온 CIC-MalMem-2022 CSV (공식 사이트에서 전체 데이터를 구할 수 없었다고 씀) |
| 전처리 | 값이 항상 0인 특징 3개 제거 → 52개. 최소-최대 정규화는 **학습 분할에서만 적합**해 누수 방지 |
| 분할 | 80/20 (4클래스 기준 **층화**), 학습 데이터에서 **5겹 층화 교차검증** — 교차검증 안에서도 정규화를 접힘마다 따로 적합 |
| 모델 | 가우시안 나이브 베이즈, 로지스틱 회귀, KNN, MLP, 결정트리, 랜덤 포레스트, 그래디언트 부스팅, LightGBM, XGBoost — **9개** |
| 지표 | 정확도, 균형 정확도, 재현율, 정밀도, F1, **MCC**, ROC-AUC, 로그 손실 |
| 시각화 | PCA로 2차원에 그려 클래스 분리 정도를 확인 |

## 5. 결과

### 5.1 이진 분류
- 5겹 교차검증에서 **9개 모델 모두 정확도·F1 99% 초과**
- 시험 분할에서 랜덤 포레스트, 그래디언트 부스팅, LightGBM은 모든 지표 **1.0000**
- 최종 선택한 XGBoost: 정확도·F1 **99.98%** — 속도와의 균형을 고려해 선택

### 5.2 4클래스 분류
- XGBoost: 정확도 87.54%, F1 81.26%. 정상을 뺀 악성 세 유형의 평균 F1은 **75.03%**
- 저자는 정상 클래스의 높은 성능이 전체 지표를 **부풀린다**고 지적하고 클래스별 지표를 따로 보고했다

### 5.3 PCA로 본 데이터
> 정상과 악성은 **뚜렷이 분리되는 두 무리**로 보인다. 그러나 악성끼리는 랜섬웨어, 스파이웨어, 트로이 목마를 구분하기 어렵다.

### 5.4 가장 중요한 특징
XGBoost의 특징 중요도 1위는 이진·다중 모두 **`svcscan.nservices`**(실행 중인 서비스 수)였고, 이진 분류에서는 나머지 특징의 중요도가 훨씬 낮았다.

## 6. ⭐ 한계 절 — 이 문서의 핵심

저자는 데이터셋 자체의 한계를 정확히 짚었다.

**① 같은 샘플의 덤프가 학습과 시험에 섞인다**
> 데이터셋은 같은 샘플에서 15초 간격으로 덤프를 최대 10번 떴다. 악성은 2,916개 샘플에서 29,298건, 정상은 **밝혀지지 않은 수의** 애플리케이션에서 29,298건이 나왔다. 누수를 피하려면 **한 샘플의 덤프가 모두 학습이나 시험 한쪽에만 들어가도록** 나누는 것이 낫다. 같은 샘플에 고유한 특성을 배운 뒤 같은 샘플로 시험하면 시험 성능이 좋아 보이고, 다른 샘플로의 일반화에 대해 잘못된 결론을 내릴 수 있다.

**② 정상은 묶을 방법이 없다**
> 현재 형식에서 이 방식은 **악성에는 가능하지만 정상에는 불가능**하다. 정상 샘플에는 고유 식별자와 번호가 없다.

**③ 특징이 논문과 맞지 않는다**
> CSV의 특징이 논문 설명과 완전히 일치하지 않는다. 예컨대 **API 후킹 특징**(전체 수, 인라인, 사용자 모드)이 없다.

**④ 분류 체계가 섞여 있다**
> 랜섬웨어와 스파이웨어는 악성코드의 **목적**이고, 트로이 목마는 정상 프로그램으로 위장하는 **구현 방식**이다. 트로이 목마 방식으로 랜섬웨어나 스파이웨어를 만들 수 있으므로, 유형 구분의 기준이 섞여 있다.

### 본 연구와의 관계

| Nassar의 지적 | 본 연구 |
|---|---|
| ① 같은 샘플 누수 | 표 1에서 **악성 덤프를 실행 단위로 묶어** 교차검증. 무작위 분할과의 차이는 깊이 3에서 약 0.04%p |
| ② 정상은 묶을 수 없음 | 표 1에서 정상은 **행 단위로 독립** 처리할 수밖에 없었음. 원 논문의 SMOTE 과표집까지 고려하면 정상 쪽 누수 가능성이 남음 → 6장 한계 후보 |
| ③ API 후킹 특징 부재 | 본 연구 데이터에서도 확인 — 원 논문의 "58개"와 공개 데이터의 "55개"의 차이(58 − 3 = 55)가 이것으로 설명됨 |

①은 본 연구가 **처음 생각해 낸 것이 아니다.** 본 연구 원고는 실행 단위 묶음을 "처음 시도한다"고 쓰지 않았으므로 문제는 없지만, 같은 문제를 먼저 지적한 문헌이 있다는 사실은 알고 있어야 한다.

## 7. 비판적으로 읽기

### 7.1 출처의 성격
- 수업 과제 보고서이며 동료 심사를 거치지 않았다. **수치**를 선행 연구의 근거로 쓰기에는 다른 학회·학술지 논문과 무게가 다르다
- 그러나 **방법론적 지적**(누수, 식별자 부재, 특징 불일치)은 데이터로 확인할 수 있는 사실이고, 실제로 본 연구 데이터로 확인되었다

### 7.2 이 보고서가 잘한 것
- 정규화를 학습 분할에서만, 교차검증 안에서는 접힘마다 따로 적합했다 — 누수를 피하는 올바른 절차
- 정확도 외에 MCC와 균형 정확도를 보고했다
- 다중 분류에서 정상 클래스가 전체 지표를 부풀린다고 지적하고 클래스별 지표를 따로 보았다
- 원 논문이 분할 방식을 밝히지 않아 비교가 어렵다는 점, 시간 측정이 하드웨어에 좌우된다는 점을 스스로 밝혔다

### 7.3 이 보고서의 한계
- 누수를 지적했지만 **실제로 묶어서 다시 평가하지는 않았다** — 향후 과제로 남겼다. 따라서 99.98%도 덤프 단위 분할의 결과다
- 서비스 수가 가장 중요하다는 것을 보고했지만 그 의미는 해석하지 않았다
- 시간 측정에서 150개가 200개보다 오래 걸리는 등 측정값이 고르지 않다(원문 표 4)

## 9. 스스로 점검하기

**Q1.** 이 보고서가 지적한 데이터 누수는 정확히 무엇인가?
<details><summary>답</summary>같은 샘플을 실행해 뜬 덤프 여러 개가 학습과 시험에 나뉘어 들어가는 것. 모델이 그 샘플에 고유한 특성을 배운 뒤 같은 샘플로 시험받으므로 성능이 실제보다 좋아 보인다.</details>

**Q2.** 이 누수를 악성에서는 막을 수 있는데 정상에서는 막을 수 없는 이유는?
<details><summary>답</summary>악성 덤프는 파일명에 계열·해시·번호가 있어 같은 실행끼리 묶을 수 있지만, 정상 덤프는 파일명이 모두 "Benign"이라 어느 덤프가 같은 출처인지 알 수 없다.</details>

**Q3.** 원 논문의 "특징 58개"와 공개 데이터의 "55개"가 다른 이유는?
<details><summary>답</summary>공개 데이터에 API 후킹 특징 3개(전체, 인라인, 사용자 모드)가 없기 때문이다. 원 논문의 새 특징 26개 중 Apihooks 범주가 정확히 3개다.</details>

**Q4.** 동료 심사를 거치지 않은 보고서를 어떻게 다뤄야 하는가?
<details><summary>답</summary>수치를 선행 연구의 성과로 묶어 인용하는 데는 신중해야 하지만, 데이터로 확인할 수 있는 방법론적 지적은 그 가치를 따로 판단할 수 있다. 출처의 성격과 내용의 가치는 구분해서 본다.</details>

**Q5.** 이 문헌을 처음 판단할 때 무엇을 놓쳤는가?
<details><summary>답</summary>초록만 읽고 "수업 과제 보고서의 99.98%"로만 판단했다. 본문의 한계 절에 본 연구의 핵심 쟁점이 있었다. 출처의 성격만으로 문헌을 판단하지 말고 내용을 읽어야 한다.</details>
