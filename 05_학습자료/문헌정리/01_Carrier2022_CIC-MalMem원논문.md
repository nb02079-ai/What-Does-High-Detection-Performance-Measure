# Carrier et al. (2022) — CIC-MalMem-2022를 만든 원 논문

> **서지**: Carrier, T., Victor, P., Tekeoglu, A., & Lashkari, A. H. (2022). Detecting obfuscated malware using memory feature engineering. *Proceedings of the 8th International Conference on Information Systems Security and Privacy (ICISSP 2022)*, Vol. 1, pp. 177–188. doi:10.5220/0010908200003120
> **소속**: 뉴브런즈윅대 캐나다 사이버보안연구소(CIC), 존스홉킨스대 응용물리연구소
> **확인 수준**: ✅ 본문 전체 (SciTePress 원문, 2026-10-01)

---

## 1. 한 줄 요약

메모리 덤프에서 특징 58개를 뽑는 도구(VolMemLyzer-V2)를 만들고, 난독화 악성코드 탐지용 데이터셋 **CIC-MalMem-2022**를 구축한 뒤, 2층 스태킹 앙상블로 정확도 99%를 보고한 논문이다.

## 2. 왜 이 논문을 읽나

본 연구 4.1절이 분석한 데이터셋의 **출생 기록**이다. 깊이 1의 결정트리 하나가 왜 99.65%를 얻는지 해석하려면, 데이터가 **어떻게 만들어졌는지** 알아야 한다. 이 논문은 그 답의 일부를 담고 있다 — 그리고 본 연구 원고에 아직 반영하지 않은 중요한 사실(정상 샘플의 SMOTE 과표집)도 여기서 나왔다.

---

## 3. 미리 알아둘 개념

| 개념 | 쉬운 설명 |
|---|---|
| **메모리 덤프** | 실행 중인 컴퓨터의 RAM 내용을 그대로 파일로 떠낸 것. 그 순간 어떤 프로세스·서비스·DLL이 떠 있었는지가 담긴다 |
| **메모리 포렌식** | 메모리 덤프를 분석해 무슨 일이 있었는지 알아내는 기법. 디스크에 흔적을 남기지 않는 악성코드도 실행 중에는 메모리에 있다 |
| **Volatility** | 메모리 덤프를 분석하는 오픈소스 도구 모음. 플러그인마다 프로세스 목록, 핸들, 서비스 등을 뽑아낸다 |
| **난독화 악성코드** | 탐지를 피하려고 코드를 암호화하거나 정상 프로세스에 숨어드는 악성코드 |
| **스태킹 앙상블** | 여러 모델(기반 모델)의 예측을 다시 입력으로 받아 최종 판정을 내리는 모델(메타 모델)을 두는 방식. 본 연구의 모델 C와 같은 구조 |
| **SMOTE** | 소수 클래스의 샘플 수를 늘리는 과표집 기법. 기존 샘플 사이를 **보간**해 새 합성 샘플을 만든다. 똑같은 샘플을 복사하지는 않지만, 원본과 거의 같은 값의 샘플이 생긴다 |

---

## 4. 논문이 풀려는 문제

저자들은 기존의 메모리 기반 악성코드 탐지가 **복잡하고 시간이 많이 걸려** 실제 적용이 어렵다고 보았다. 그래서 두 가지를 목표로 삼았다.

1. 메모리에서 뽑은 **가볍고 효과적인 특징**으로 빠르게 탐지하는 방법
2. 실제 환경에 최대한 가까운, **난독화 악성코드에 초점을 맞춘 데이터셋**

## 5. 방법

### 5.1 특징 — VolMemLyzer-V2

메모리 덤프를 Volatility(2.6)로 분석하고, 그 결과를 VolMemLyzer가 **특징 58개**로 정리해 CSV 파일로 만든다. 이 중 **26개가 새로 추가**된 특징으로, 다섯 범주에 속한다.

| 범주 | 무엇을 보는가 |
|---|---|
| Malfind | 악성일 가능성이 있는 실행 코드(주로 트로이 목마의 DLL) |
| Ldrmodule | 주입된 코드의 흔적(스파이웨어가 흔히 쓰는 방식) — 모듈 목록에서 빠진 모듈 수 등 |
| Handles | 포트·파일·이벤트·레지스트리 키·스레드 등 핸들의 종류별 개수 |
| Process View | 여러 방식으로 본 프로세스 목록 사이의 불일치 비율 |
| Apihooks | API 후킹의 수 |

메모리 덤프 하나는 2GB지만, 특징을 뽑은 결과 CSV 파일은 약 2KB로 줄어든다.

### 5.2 데이터셋 — CIC-MalMem-2022

| 항목 | 내용 |
|---|---|
| 규모 | 58,596건 — 정상 29,298 / 악성 29,298 |
| 악성 샘플 | VirusTotal에서 모은 **2,916개**. 3대분류 × 계열 5개씩 = 15개 계열 |
| 실행 환경 | 메모리 2GB의 **Windows 10** 가상 머신(Oracle VirtualBox), 격리 |
| 덤프 방법 | 가상 머신 **바깥에서** 캡처 — 덤프 프로그램이 메모리에 섞여 들어가지 않도록 |
| 덤프 횟수 | 샘플 하나를 실행할 때마다 **15초 간격으로 10개** |
| 악성 실행 시 | **여러 애플리케이션을 함께 열었다** — "분류기가 정상 프로세스만으로 차이를 판별하지 못하게 하려고" |
| 정상 덤프 | 기계에서 여러 애플리케이션을 쓰는 **일상 행위를 캡처**한 뒤, 균형을 맞추려고 **SMOTE로 과표집** |

**15개 계열과 샘플 수 (원문 표 2)**

| 대분류 | 계열 (샘플 수) |
|---|---|
| 트로이 목마 | Zeus 195, Emotet 196, Refroso 200, Scar 200, Reconyc 157 |
| 스파이웨어 | 180Solutions 200, Coolwebsearch 200, Gator 200, Transponder 241, TIBS 141 |
| 랜섬웨어 | Conti 200, Maze 195, Pysa 171, Ako 200, Shade 220 |

### 5.3 탐지 모델 — 2층 스태킹

- **1층(기반 모델)** 후보: SVM, 결정트리, 선형 퍼셉트론, 나이브 베이즈, 랜덤 포레스트, KNN 중 **3개**
- **2층(메타 모델)** 후보: SVM, KNN, 나이브 베이즈, 로지스틱 회귀
- 여러 조합을 실험해 가장 좋은 것을 골랐다

## 6. 결과

**개별 분류기 (원문 표 3, 정확도)**

| RF | 결정트리 | KNN | 나이브 베이즈 | SVM | 선형 퍼셉트론 |
|---|---|---|---|---|---|
| 0.97 | 0.97 | 0.95 | 0.92 | 0.90 | 0.60 |

**스태킹 조합 상위 4개 (원문 표 4, 정확도)**

| 기반 모델 | 메타 모델 | 정확도 |
|---|---|---|
| 나이브 베이즈, 선형 퍼셉트론, 결정트리 | SVM | 0.95 |
| SVM, 선형 퍼셉트론, 결정트리 | KNN | 0.96 |
| 나이브 베이즈, 선형 퍼셉트론, RF | 로지스틱 회귀 | 0.97 |
| **나이브 베이즈, RF, 결정트리** | **로지스틱 회귀** | **0.99** |

**최종 결과**: 정확도 **99.00%**, F1 **99.02%**

## 7. 비판적으로 읽기

### 7.1 원문에 없는 것
- **학습·시험 분할 방식이 서술되어 있지 않다.** 어떤 데이터로 학습하고 어떤 데이터로 99%를 측정했는지 알 수 없다. 실행 하나에서 덤프가 10개 나오므로, 무작위로 나누면 같은 실행의 덤프가 학습과 시험에 함께 들어갈 수 있다
- **실제로 수집한 정상 덤프의 수**를 밝히지 않았다. SMOTE로 몇 배를 늘렸는지 알 수 없다

### 7.2 논문 안의 불일치
| 항목 | 한 곳 | 다른 곳 |
|---|---|---|
| 특징 수 | 본문 "58개 추출" | 공개 데이터셋은 55개 |
| 판정 시간 | 본문 "샘플당 약 0.008ms" | 표 5: 50개에 0.4초 → 샘플당 **약 8ms** |

### 7.3 ⭐ 정상 샘플의 SMOTE 과표집 — 본 연구에 중요
- 정상 클래스에 **합성 샘플이 섞여 있다**는 뜻이다. 합성 샘플은 실제 샘플 사이를 보간해 만들므로, 정상 클래스의 다양성이 실제보다 작을 수 있다
- 본 연구가 공개 데이터를 확인한 결과, 개수형 특징에 소수점 값이 있는 행은 정상 0.6%, 악성 0.4%로 비슷했고 정상의 서비스 수는 모두 정수였다. 정상 파일명은 전부 `Benign`이라 실제와 합성을 구별할 방법도 없다. 따라서 **합성 샘플이 얼마나 되는지는 확인할 수 없다**
- 본 연구의 표 1은 악성 덤프만 실행 단위로 묶었다. 정상에 원본과 그 합성본이 함께 있다면, 둘이 학습과 평가에 나뉘어 들어갈 수 있다 → 원고에 반영할지 **결정 대기**

### 7.4 저자들의 통제와 본 연구의 관찰
- 저자들은 악성 실행 때도 애플리케이션을 함께 열어 "정상 프로세스만으로 구별되지 않게" 하려 했다
- 그런데 본 연구에서는 **실행 중인 서비스 수 하나**로 99.65%가 나왔다. 저자들이 의도한 통제가 서비스 구성의 차이까지 막지는 못했을 가능성이 있다. 다만 그 차이가 수집 절차에서 왔는지 악성코드의 행위에서 왔는지는 데이터만으로 가릴 수 없다(본 연구 4.1)

### 7.5 스태킹의 이득
- 개별 랜덤 포레스트가 이미 0.97이고 최종 스태킹이 0.99다. 결합의 이득은 약 2%p다. 본 연구의 스태킹(모델 C)이 성능을 바꾸지 못한 것과 비교해 볼 만하다 — 다만 이 논문은 분할 방식이 불분명해 직접 비교는 어렵다

## 8. 본 연구 원고와의 연결

| 원고 위치 | 쓰임 |
|---|---|
| 1장 ¶2, 2.2.3 | "원 논문은 99%의 정확도를 보고했다" |
| 4.1.1 | 정상과 악성이 **같은 Windows 10 가상 머신**에서 수집되었다는 사실 → 서비스 수 차이의 두 가지 해석 |
| 4.1 표 1 | 실행 하나에서 덤프 10개 → 실행 단위로 묶은 교차검증의 근거 |
| 4.1 각주 | 본 연구가 복원한 실행 2,906개 vs 원문 2,916개 |
| **결정 대기** | ① SMOTE 과표집을 4.1에 언급할지 ② 6장 한계로 넣을지 ③ 원문으로 확인된 "스태킹 앙상블"을 서론·2.2.3에 되살릴지 |

## 9. 스스로 점검하기

**Q1.** 샘플 하나를 실행할 때 메모리 덤프를 몇 개 떴는가? 이것이 평가에 왜 중요한가?
<details><summary>답</summary>15초 간격으로 10개. 같은 실행의 덤프들은 서로 매우 비슷하므로, 무작위로 나누면 학습과 시험에 같은 실행의 덤프가 함께 들어가 성능이 부풀려질 수 있다. 본 연구가 실행 단위로 묶어 교차검증한 이유다.</details>

**Q2.** 정상 덤프를 SMOTE로 과표집했다는 사실은 평가에 어떤 영향을 줄 수 있는가?
<details><summary>답</summary>정상 클래스에 원본과 거의 같은 합성 샘플이 섞이므로, 원본이 학습에, 합성본이 시험에 들어가면 시험이 쉬워진다. 또한 정상 클래스의 실제 다양성이 작아 보일 수 있다. 다만 공개 데이터에서 합성 샘플의 비율은 확인할 수 없었다.</details>

**Q3.** 저자들은 왜 악성코드를 실행할 때도 애플리케이션을 함께 열었는가? 본 연구의 관찰은 이 의도와 어떤 관계인가?
<details><summary>답</summary>분류기가 "정상 프로세스가 떠 있는지"만으로 클래스를 가르지 못하게 하려고. 그러나 본 연구에서 서비스 수 하나로 99.65%가 나왔으므로, 그 통제가 서비스 구성의 차이까지 막지는 못했을 가능성이 있다.</details>

**Q4.** 최종 스태킹 모델은 개별 랜덤 포레스트보다 얼마나 나았는가?
<details><summary>답</summary>약 2%p (0.97 → 0.99). 다만 분할 방식이 서술되지 않아 이 차이가 얼마나 믿을 만한지는 판단하기 어렵다.</details>

**Q5.** 원 논문의 "99%"를 인용할 때, 정확도와 F1을 구분해야 하는 이유는?
<details><summary>답</summary>원문은 정확도 99.00%, F1 99.02%다. 다른 논문(Shafin et al., 2023)은 이를 "정확도 99.02%"로 인용했다. 2차 인용에서 지표가 뒤섞이는 실제 사례다.</details>
